第一篇・GITHUB／1.1

為什麼需要版本控制

情境

賽前最後一晚，你想再壓一點常數。為了保險，你先「另存新檔」：final.cpp、final_v2.cpp、final_v2_真的.cpp……凌晨一點，程式突然 WA。你只想回到「兩小時前那個能跑的版本」——但它是哪個檔？

這個場景每個寫過程式的人都經歷過。「另存新檔」其實就是在手動做版本控制，但它有三個致命缺陷：版本沒有順序（檔名排不出時間線）、版本沒有說明（v2 和 v2_真的 差在哪？）、版本之間不能比對（只能肉眼找不同）。Git 把這三件事全部自動化。

版本控制系統（Version Control System, VCS）做的事情就是右邊這條線：只保留一份工作中的檔案，把每個時間點的完整狀態存成「快照」，快照之間串成有順序、有說明、可比對、可回復的歷史。Git 是目前這個星球上絕對主流的 VCS——你之後會用到的所有開源專案、公司、競賽隊伍，都跑在它上面。

核心觀念

「回得去」不只是保險，它會改變你寫程式的行為：因為任何修改都可以整包撤銷，你才敢大膽重構、大膽實驗。版本控制是勇氣的基礎建設。

那 GitHub 又是什麼？

常見的混淆：Git 是工具，GitHub 是網站。Git 在你的電腦上管理版本歷史；GitHub 是雲端上放 Git 倉庫的地方，讓多人共享同一份歷史，並在上面長出協作功能（Pull Request、Issue、code review）。關係就像「中文」與「一個大家都在用的中文論壇」。1.2–1.5 先講 Git 本體，1.6 之後才上 GitHub。

第一篇・GITHUB／1.2

Git 心智模型：快照、hash、DAG

情境

教學影片常把 Git 講成一堆要背的指令，背完還是不懂它在幹嘛。其實 Git 的資料結構你早就認識——它就是一張有向無環圖（Directed Acyclic Graph, DAG），每個節點是一份完整快照。用圖論來學，十分鐘就能建立正確的模型。

Git 的世界只有一種核心物件需要先認識：commit（提交）。一個 commit 包含三件事：

  • 一份完整快照：當下所有被追蹤檔案的內容（不是差異，是整包狀態）；
  • 中繼資料：作者、時間、一句訊息（這次改了什麼）；
  • 指向 parent 的指標：它是從哪（幾）個 commit 演化來的。

每個 commit 用內容算出一個雜湊值（SHA-1，像 a1f9c3e…）當作身分證。內容決定 hash——所以歷史不可竄改：改了任何一個字，hash 就變了，等於是另一個 commit。

給競程選手的翻譯

commit＝節點；「指向 parent」的邊構成一張 DAG（合併節點有兩個 parent，所以是圖不是樹）；git log＝從某個節點出發走訪祖先；分支＝指向某節點的指標（下一節細講）；兩個分支的共同祖先＝最近共同祖先（Lowest Common Ancestor, LCA）——Git 合併時真的就在找它。

常見誤解

「commit 存的是這次改動的 diff。」——不對。每個 commit 都是完整快照，你看到的 diff 是 Git 臨時比對兩個快照算出來的。方向也別記反：箭頭永遠從新指向舊（child 記著 parent），因為未來無法預知，過去不可改變。

三區模型：你的檔案到底在哪裡

情境

你改了三個檔案，但只有其中一個跟「新增單字」有關，另外兩個是順手調的排版。你想把它們分成兩次提交，讓歷史乾淨——Git 怎麼知道哪次提交要包含哪些檔案？答案是中間多了一站：暫存區。

Git 把「你的檔案」分成三個區域。理解這張圖，之後所有指令都只是「把東西從一區搬到另一區」：

  • 工作區（working directory）：你實際編輯的資料夾，想怎麼改就怎麼改；
  • 暫存區（staging area）：下一次提交的「打包清單」，git add 把改動放上去；
  • 儲存庫（repository）：.git 資料夾裡的歷史 DAG，git commit 把暫存區的內容變成新節點。
核心觀念

暫存區存的是你執行 add 那一刻的內容，之後檔案再怎麼改都不影響它。這正是它存在的意義：讓你精準控制「下一個 commit 要包含什麼」，把不相干的改動拆成乾淨的多次提交。迷路時，先打 git status——它永遠會告訴你三區現在的狀態，以及下一步可用的指令。

第一篇・GITHUB／1.4

個人日常指令：循環與時光機

情境

你重構了 solve()，跑起來卻比原本慢三倍，而且你已經忘了自己動過哪幾行。「把這個檔案變回上一次 commit 的樣子」、「看看我到底改了什麼」——這兩件事各只要一個指令。

第一次使用：報上名來

Git 會把作者姓名與 email 寫進每個 commit（記得嗎？commit 的中繼資料）。第一次使用前設定一次即可：

$ git config --global user.name "Lin Hua"
$ git config --global user.email "you@example.com"
地雷

這裡的 email 之後要與你的 GitHub 帳號綁定的 email 一致，GitHub 才會把 commit 正確算到你頭上（貢獻紀錄、評審查作者都看這個）。換電腦、換系統時最容易忘記重設。

日常循環：三個指令佔九成

個人開發的節奏就是不斷重複這個循環——每完成一小步就提交一次：

$ git status                       # 現在三區什麼狀態？（迷路先打這個）
$ git add words.json               # 把改動放上打包清單（. 代表全部）
$ git commit -m "feat: 新增動物主題單字 20 個"

提交前想確認自己改了什麼，用 diff；想回顧歷史，用 log：

$ git diff                         # 工作區 vs 暫存區：還沒 add 的改動
$ git diff --staged                # 暫存區 vs 上個 commit：即將提交的內容
$ git log --oneline --graph        # 每行一個 commit，畫出 DAG
* c9e1f02 feat: 新增動物主題單字 20 個
* 7b2d941 style: 卡片加上圓角與陰影
* a1f93d8 feat: 首頁骨架與單字列表

commit 訊息：寫給三個月後的自己

訊息格式採廣泛使用的慣例：類型: 一句話說明做了什麼。四種類型就夠用：

類型用途例子
feat新功能feat: 卡片點擊翻面顯示中文
fix修 bugfix: 修正單字重複出現的問題
docs文件docs: README 加入安裝說明
chore雜務（設定、整理）chore: 加入 .gitignore

三條規則：說做了什麼，不是改了哪個檔（❌ update index.html　✅ feat: 首頁加入今日複習區塊）；一個 commit 只做一件事（方便回溯與 review）；一句話、現在式。

時光機：四種救援

你想要指令說明
丟掉某檔案在工作區的修改git restore f.py把檔案變回暫存區／上次 commit 的樣子。修改直接消失，無法復原，下手前先想。
把檔案從打包清單撤下git restore --staged f.py只離開暫存區，工作區的修改還在。
修改上一個 commit（訊息或漏加檔案）git commit --amend重寫最後一個節點。已推上遠端的 commit 不要 amend（等於改歷史）。
撤銷某個歷史 commitgit revert c9e1f02做一個內容相反的新 commit 蓋回去。歷史不被改寫，最安全，團隊必用這招。
保險絲

就算真的把歷史弄壞了，git reflog 記錄著 HEAD 走過的每一步，幾乎永遠救得回來。先知道這個保險絲存在就好，用法收錄在附錄速查卡。原則：commit 了的東西很難真的丟失；沒 commit 的東西最危險。所以：勤 commit。

分支與合併：會移動的指標

情境

你想幫 VocaBuddy 加深色模式，但不確定做不做得好，也不想弄髒目前能跑的版本。要是能「開一個平行世界去實驗，成功就收編、失敗就整個丟掉」就好了。這正是分支（branch）——而且在 Git 裡開一個平行世界的成本是：新增一個指標，零複製。

上一節的 DAG 已經暗示了答案：歷史是一張圖，那「目前進度」怎麼表示？用指標。

  • branch（分支）＝ 一個指向某 commit 的具名指標。main 不是什麼特殊存在，它只是預設的那個指標；
  • HEAD ＝「你現在站在哪個分支上」的指標（指標的指標）；
  • 在分支上提交時，該分支指標自動前進到新 commit，其他指標不動。

指令對照

動作指令備註
建立分支git branch dark-mode只是新增指標，不切換過去
切換分支git switch dark-mode建立＋切換一次做完：git switch -c dark-mode
列出分支git branch* 標示 HEAD 所在
合併git merge dark-mode先 switch 到要「收編別人」的分支（通常是 main）再 merge
刪除已合併分支git branch -d dark-mode刪的是指標，commit 都還在歷史裡
給競程選手的翻譯

合併時 Git 找出兩個分支的最近共同祖先（Lowest Common Ancestor, LCA），比較「祖先 → 你這邊」與「祖先 → 對方」兩組改動，各自動了不同檔案（或同檔不同區塊）就自動合併；兩邊改到同一行才需要人類出面——那就是衝突，1.7 實地拆解。若對方是你的直系後代，連合都不用合，指標往前推即可（fast-forward）。

地雷

切換分支前，先把手上的修改 commit（或至少 git stash 暫存，用法見速查卡）。帶著未提交的修改亂切分支，是初學者搞混「這些改動屬於誰」的第一大原因。

分支怎麼命名

慣例：類型/簡短描述，全小寫、連字號分隔，例如 feature/quiz-button、fix/duplicate-words。看到名字就知道這條分支在幹嘛。

GitHub 與遠端：把倉庫放上雲端

情境

你的 VocaBuddy 目前只活在你的筆電裡。筆電如果進水，歷史整條陪葬；隊友想一起開發，也拿不到程式碼。需要一個雲端上的「共同版本」——大家都同步它、也都把進度推回它。

GitHub 上的倉庫（repository，簡稱 repo）就是那個共同版本。你的電腦與雲端各有一份完整的歷史 DAG——Git 是分散式的，沒有網路你照常 commit，有網路時再同步。三個同步動作：clone（第一次整包下載）、push（把你的新 commit 推上去）、pull（把別人的新 commit 拉下來）。

指令對照

動作指令備註
把遠端倉庫抓下來git clone https://github.com/you/ytp-vocabuddy.git整包歷史，做一次就好

核心觀念

origin/main 是本地放的一張書籤：「上次同步時，遠端的 main 在這裡」。git status 說你 ahead 2 commits，意思就是你的 main 比書籤多兩個節點——該 push 了。

地雷

push 被拒絕（rejected: fetch first）幾乎都是同一個原因：遠端有你還沒拉下來的新 commit。解法永遠是先 git pull、必要時解衝突，再 push。絕對不要照網路偏方加 --force——那會把隊友的 commit 從遠端抹掉。

README：倉庫的門面

倉庫根目錄的 README.md 會自動顯示在 GitHub 首頁，是別人（隊友、老師、評審）認識你作品的第一眼。最低限度寫四件事：這是什麼、怎麼安裝執行、用了什麼技術、誰做的。用 Markdown（一種輕量標記語言：以純文字符號表達格式）撰寫——標題 #、清單 -、程式碼區塊三個反引號，五分鐘就能上手。

另外兩個好習慣：.gitignore 檔案列出不該進版本控制的東西（編譯產物、.DS_Store、含金鑰的設定檔——金鑰進了歷史就等於公開，切記）；Issue 是倉庫的待辦清單，bug 與想做的功能都開成 issue，團隊協作時它就是任務板。

團隊協作：GitHub Flow 與 Pull Request

情境

三個人同時開發 VocaBuddy，都直接 push 到 main：星期三，倉庫裡同時存在三個人互相踩壞的版本，沒有人知道哪次 push 弄壞了首頁。團隊需要一個規則：任何改動，先給隊友看過，才進 main。這個規則有個名字——GitHub Flow。

GitHub Flow 是最普及的輕量協作流程，一句話版本：main 永遠保持可用；所有改動走分支，透過 Pull Request（PR）審核後合併。完整循環：

  1. 從 main 開一條分支（feature/quiz-button）；
  2. 在分支上開發、commit、push 上 GitHub；
  3. 在 GitHub 開 Pull Request：「請求把我的分支合併進 main」；
  4. 隊友 code review：在 PR 頁面逐行看 diff、留言討論；
  5. 需要修改就繼續在分支上 commit——PR 自動跟著更新；
  6. 核可（Approve）後合併，刪除分支，回到 1。

PR 怎麼寫、review 看什麼

PR 描述是寫給 reviewer 的說明書，固定三段就很專業：

## 做了什麼
- 卡片下方新增「考我」按鈕，點擊隨機抽一張未複習的卡
## 為什麼
- 對應 issue #8：使用者想主動測試自己
## 怎麼驗證
- 開啟 index.html → 點「考我」→ 卡片應更換且不重複

review 時看四個面向：正確性（邏輯對嗎？邊界條件呢？）、可讀性（三個月後看得懂嗎？）、一致性（跟專案既有風格一致嗎？）、安全（有沒有把金鑰、個資 commit 進來？）。留言對事不對人：「這裡如果輸入是空陣列會爆」比「你寫錯了」有用。

衝突：Git 在問你問題

兩條分支改到同一個檔案的同一行，自動合併就會停下來。這不是錯誤——是 Git 誠實地承認「機器無法決定哪邊才對」，把選擇權交給你。

解衝突的固定五步：git status 看哪些檔案衝突 → 打開檔案找 <<<<<<< → 編輯成你要的最終內容（可以保留任一邊、也可以兩邊融合）並刪掉三行記號 → git add 該檔案 → git commit 完成合併。編輯器（如 VS Code）會高亮衝突區塊並提供快速按鈕，但別無腦按「接受目前版本」——先讀懂兩邊在改什麼。

先說在前面

第五篇會教你做一個 AI 子代理，讓它在你之前先審一遍 diff。它很好用——但不取代這一節的人審。機器管「壞了沒」，人管「好不好」；一個由 AI 寫、AI 審、沒有人看過的 PR，掛的還是你的名字。

核心觀念

降低衝突的方法不是技術，是習慣：分支小、勤 pull、早合併。一條活了兩星期的大分支，合併日就是災難日；每天合一點，衝突永遠只有幾行。

最後一塊拼圖：隊友怎麼取得倉庫的推送權？倉庫擁有者到 Settings → Collaborators 邀請隊友帳號，對方接受後就能 push 分支、開 PR（開源專案的陌生貢獻者則走 fork——複製一份到自己帳號再發 PR，概念相同）。至此你已具備完整的團隊協作詞彙——Lab 2 全部實際走一遍。

什麼是代理式編碼工具

情境

你把 500 行貼進聊天視窗，它給你一段改好的碼；你貼回編輯器、存檔、跑——壞在另一個地方。你再把新的錯誤訊息貼過去⋯⋯來回第七次，你發現自己整個下午都在當人肉剪貼簿。問題不是模型不夠聰明，是它看不到你的專案，也碰不到你的鍵盤。

代理式編碼工具（agentic coding tool）解決的就是這件事。它跟聊天視窗差在三樣東西，缺一不可：

  • 工具（tools）：它能讀檔案、搜尋整個倉庫、執行終端機指令、開分支——不是描述給你聽，是真的做；
  • 權限（permissions）：因為它真的會動手，所以每個動作背後都有一個「這件事可不可以做」的關卡（5.3 細講）；
  • 迴圈（loop）：它做完不會停，會回頭驗證結果，沒過就再來一輪——直到達成你給的目標，或是卡住來問你。

這三樣加起來就是代理迴圈（agentic loop）：蒐集上下文 → 採取行動 → 驗證結果，不斷循環。

核心觀念

聊天視窗裡，這個迴圈是你在跑：你去找上下文、你去改檔案、你去跑測試、你判斷過沒過。代理式工具做的事，是把這個迴圈交給機器跑，而把你升級成驗收的人。所以這一篇真正在教的不是「怎麼下指令」，是「怎麼當一個好的驗收者」。

上下文視窗是預算，不是容器

情境

你跟它工作了三個小時，一切順利。然後它開始出怪招：把你半小時前說「不要動」的檔案改了，還把你們早就決定的命名慣例忘得一乾二淨。它不是壞掉了，也不是在跟你賭氣——是你早期講的話，已經被擠出它的視野了。

第二篇 2.4 講過上下文視窗（context window）：模型一次能看見的 token 總量，是個硬上限。在聊天視窗裡這個限制很少咬到你，因為對話通常不長。但在代理式工具裡，這是你每天都要管的資源——因為它會自己把大量檔案內容讀進來。

換個比喻

別把上下文視窗想成「一個裝得下多少東西的箱子」，想成一筆預算：每讀一個檔案、每跑一次指令、每來回一輪對話，都在花錢。花光了，最舊的東西就會被擠出去——而它不會提醒你被擠掉了什麼。

三個省預算的動作

動作做什麼什麼時候做
看用量查目前佔用了多少覺得它開始變鈍時，先看一眼再決定下一步
壓縮把前面的對話濃縮成摘要，騰出空間同一件任務還沒做完、但歷史太長時
清空整段歷史丟掉，從乾淨狀態重來換一件不相干的任務時。這是最被低估的一招

各家的指令名稱不同（Claude Code 是 /context、/compact、/clear），但這三個動作是共通的。查你的工具怎麼叫它們，然後把它們用成反射動作。

最實用的一條習慣

一個任務、一個乾淨的工作階段。做完「修好翻面 bug」就清空，再開始「加深色模式」。不要讓一個工作階段從早開到晚——那不是節省，那是讓它拖著一堆不相干的記憶做事，又慢又容易出錯。

壓縮的代價，以及正確的解法

壓縮會保留「大意」、丟掉「細節」。所以你們花二十分鐘討論出來的重要決定，如果只存在對話歷史裡，壓縮之後它就可能不記得了。

正解不是「不要壓縮」，是重要的東西不要只放在對話裡——寫進檔案。這正是下一節的主題。

權限與紅線：哪些事永遠不放手

情境

連續二十次它都做得又快又對，你開始覺得每次都按確認很煩，於是切到自動接受。十分鐘後，你看到終端機捲過一行 git push --force。遠端的歷史被覆蓋了，而那上面有隊友昨晚的三個 commit。

代理式工具的能力來自「它真的會動手」，風險也來自同一句話。所以每個動作背後都有一個權限關卡。要管好它，先把動作分級——依「錯了以後救不救得回來」來分，不是依「難不難」。

認得這張階梯嗎

它跟 4.4 的安全階梯是同一套思路：不是把所有事都當成危險，而是分級之後，把注意力集中在真正回不去的那一階。全部都問你，你會麻痺；全部都放手，你會出事。分級才有辦法長期做對。

四條紅線

不管你多熟、工具多好用，這四件事永遠自己按：

  • 推上遠端——尤其是任何形式的強制推送。遠端是全隊共用的，你的失誤會變成別人的失誤；
  • 刪除——刪檔案、刪分支、重設歷史。commit 過的救得回，沒 commit 的救不回（第一篇 1.4）；
  • 金鑰與個資——任何讀取、貼上、送出金鑰的動作。這條在 4.4 已經講過一次，這裡再講一次；
  • 對外送出——把你的程式碼或資料送到你沒檢查過的地方。
給比賽的提醒

競賽期間，你的 repo 是評審檢視的對象，歷史紀錄本身就是作品的一部分。讓工具自動推送，等於把「歷史長什麼樣」交給它決定。比賽期間請一律維持：本機可以放手，推上遠端一定自己來。

怎麼設，才不會每天被問到煩

好的設定長這樣：把第 1、2 階設成不用問，第 3、4 階一律問。各家做法不同（有的用權限模式，有的可以逐項設定允許清單），但目標一致——讓確認鍵出現在值得你停下來的時候。

如果你發現自己在無意識地連按確認，那不是你不專心，是設定太吵了。回頭調設定，別調自己。

專案指示檔：把隊規寫下來

情境

你的 AI 產生 2 空格縮排，隊友的產生 4 空格；你的寫 const，他的寫 var；你的 commit 訊息是 feat: …，他的是 Update index.html。PR 打開一看，八成的差異是空白和風格，真正的邏輯改動淹沒在裡面。你們兩個都沒做錯——你們只是各自對著一個不知道隊規的 AI 說話。

解法很簡單，簡單到有點反高潮：把隊規寫成一個檔案，放進倉庫。這個檔案叫專案指示檔——每次工具在這個專案裡啟動，它會自動讀。你不用每次重講，隊友也不用。

為什麼它必須進版本控制

因為它是隊規，不是個人偏好。進了 Git，它就跟程式碼一樣有歷史、可以在 PR 裡討論、改動要經過 review。「我們決定 commit 訊息用這個格式」從一句口頭約定，變成一行可追溯的 commit——這正是第一篇教你的那件事，只是這次管的是 AI 的行為。

寫什麼？五個段落就夠

指示檔不是愈長愈好——它每次啟動都在花你的上下文預算（5.2）。太長，它讀不完也記不牢；太雜，重點被稀釋。一份好的指示檔通常只有這五段：

段落寫什麼VocaBuddy 的例子
這是什麼專案兩三句話講清楚做什麼、給誰用「背單字網頁，純前端，資料存 localStorage，無後端」
怎麼跑起來怎麼開、怎麼測「本地起一個 http 伺服器再開（例如 python3 -m http.server，瀏覽 localhost:8000）；SRS 測試跑 node test_srs.js」　←　Lab 9 之後 App 是 PWA，file:// 開會讓 service worker 註冊失敗；指示檔寫錯一次，AI 之後會一直叫你用 file://
程式碼慣例縮排、命名、用不用框架「2 空格縮排；不引入任何框架與套件；函式用小駝峰」
協作規矩commit 訊息格式、分支命名、PR 規矩「commit 用 類型: 說明；分支 feature/…；不直接推 main」
不要做的事紅線與雷區「不要動 words.js 的資料格式；不要把金鑰寫進程式碼；不要自動推遠端」
寫指示檔的三條經驗法則

一、寫具體的，不寫抽象的。「程式碼要乾淨」沒有用，「2 空格縮排、函式不超過 40 行」才有用。
二、寫你真的在乎的，不寫你聽說很好的。每一條都會佔預算，抄一堆用不到的規則只是把重點稀釋掉。
三、被同一件事煩到第二次，就寫進去。這是最好的判斷標準——指示檔應該是長出來的，不是一次寫完的。

檔名不一致，就架一座橋

5.1 的表看過了：各家讀的檔名不同，而且 Claude Code 官方明講它不讀 AGENTS.md。如果你的隊伍裡有人用不同工具，兩個選擇——

① 匯入：留一份 AGENTS.md 當本體，在 CLAUDE.md 裡用 @AGENTS.md 把它引進來。
② 符號連結（symbolic link）：讓兩個檔名指向同一份內容。

兩種都可以，重點是只維護一份真本。最糟的作法是兩個檔案各寫各的——過三天你們就會有兩套互相矛盾的隊規，而且沒人知道哪份是真的。（想起第一篇 1.0「單一事實來源」了嗎？同一個道理。）

Lab 12：讓 AI 認識你的專案

目標寫一份專案指示檔，走完整的 issue → 分支 → PR → merge，並驗證它真的生效
時間約 40 分鐘
前置Lab 11 完成（工具能讀到你的專案）

  1. 開一個 issue，說清楚你要什麼

    在 GitHub 上開 issue：「新增專案指示檔，統一 AI 產出的程式碼風格與 commit 格式」。內文寫下你想定的三條規矩就好——沿用第一篇 1.7 的習慣，先有 issue 再動手。

  2. 開分支

    $ git switch -c feature/project-instructions

  3. 請它草擬，然後你改

    這一步刻意不叫你從零開始寫——讓工具先讀過整個專案再草擬，它比你更清楚倉庫裡實際長什麼樣：

    請先讀過這個倉庫的所有檔案，然後幫我草擬一份專案指示檔，
依這五個段落：這是什麼專案／怎麼跑起來／程式碼慣例／協作規矩／不要做的事。
慣例的部分請從現有程式碼「觀察」出來，不要憑空建議。
全部用繁體中文，總長度控制在 60 行以內。

    檔名依你的工具而定（Claude Code 用 CLAUDE.md，Codex 用 AGENTS.md，其餘見 5.1 的表），放在倉庫根目錄。

    這一步最容易偷懶，而偷懶會反噬

    草稿一定要逐行改過。它會寫出一些「看起來很專業但你們根本不做」的規矩（例如要求寫單元測試覆蓋率、用某個 linter）。這些條目留著只有壞處：佔預算、而且會讓 AI 產出你們不想要的東西。刪到只剩你真的在乎的。

  4. 驗證它真的生效——這是本 Lab 的重點

    寫完不代表有用。用一個對照實驗來驗：

    • 在指示檔裡寫一條容易辨識的規矩。這條規矩要挑「模型照抄現狀也不會自然做到」的事——「新函式加一行繁體中文註解」就不合格：你的倉庫本來就全是中文註解，它會模仿既有風格照做，你得到的是假陽性。改成有固定記號的寫法，例如「每個新函式上方加一行 // 用途：…」；
    • 更保險的做法是先跑對照組：在還沒放指示檔時，用同樣的話請它加一個函式，看它會不會自己做到那條規矩。會做到的，換一條；
    • 清空目前的工作階段（5.2 學的），讓它重新讀一次指示檔；
    • 請它加一個小函式，例如「在 index.html 加一個 shuffleWords() 把單字順序打亂」；
    • 看它有沒有自動加上那行中文註解——你完全沒提，它卻做了，那就是指示檔生效了。

    沒生效？看下面的「卡住了？」。

  5. 提交、發 PR、請隊友 review

    $ git add CLAUDE.md          # 或你的工具對應的檔名
$ git commit -m "docs: 新增專案指示檔，統一 AI 產出風格"
$ git push -u origin feature/project-instructions

    到 GitHub 發 PR，內文寫 Closes #你的 issue 編號。請隊友真的看過再 merge——這份檔案會影響全隊每一次 AI 產出，它值得一次認真的 review。這也是為什麼它該進版控：一份口頭約定沒辦法被 review。

卡住了？

① 指示檔沒生效——依序檢查三件事：檔名對不對（見 5.1 的表，大小寫也要對）？在倉庫根目錄還是放到子資料夾去了？有沒有清空舊工作階段（舊階段不會重新讀檔）？
② 它說找不到那個檔案——你可能在別的資料夾啟動了工具（Lab 11 步驟 2 的第 ③ 步）。
③ 草稿長到 200 行——正常，它很愛寫。你的工作就是刪，刪到 60 行以內。刪不下手時問自己：「這條規矩，我這禮拜真的會在意嗎？」
④ 它寫了倉庫裡根本沒有的東西（例如提到不存在的測試指令）——這是幻覺（第二篇 2.1）。刪掉，並在提示裡加一句「只根據你實際讀到的檔案寫」。
⑤ git push 被拒——回第一篇 1.6 的遠端章節；多半是還沒設 upstream，用上面那行帶 -u 的指令。
⑥ 隊友用不同工具，檔名不一樣——用 5.4 的橋接法（匯入或符號連結），只維護一份真本。

驗收清單

你剛剛做的事，比看起來重要

這份檔案是你的隊伍第一次用版本控制去管理 AI 的行為。從今天起，「我們是怎麼寫程式的」不再是三個人腦袋裡三個版本，而是倉庫裡一份可以討論、可以修改、可以追溯的檔案。下一節要教的技能，是同一個想法再往前一步。

技能與子代理：教一次，用很多次

情境

「幫我新增一批單字：先讀 words.js 看格式，加完跑 node check_words.js，通過再開分支 commit，訊息用 feat: 開頭……」這段話你這禮拜貼了第九次。而且每次都少講一句，每次它就少做一件事。

5.4 的專案指示檔解決了「每次都要講的隊規」。但還有一種東西不該進指示檔——只在特定任務才用得到的做法。全部塞進指示檔，它每次啟動都得讀一遍你的新增單字流程，就算你今天只是要改個按鈕顏色。這是在燒上下文預算（5.2）。

這類東西有它自己的位置，叫技能（skill）。

一句話分清楚

專案指示檔＝「這個專案永遠要遵守的事」，每次都讀。
技能＝「做某一類任務時才要照的步驟」，符合時才讀。
差別在「永遠」與「某一類」——用這條線分，幾乎不會分錯。

技能長什麼樣

一個技能就是一個資料夾，裡面放一份 SKILL.md。開頭是一段 YAML 前置資料（frontmatter），只有兩個欄位必填：

---
name: add-words
description: 新增或修改 words.js 的單字時使用。包含格式規範、
  重複檢查，以及提交前必跑的 check_words.js 驗證流程。
---

# 新增單字流程

1. 先讀 words.js 確認現有格式（en / zh 兩個欄位，不要自創欄位）
2. 加在陣列最後，不要重排既有順序
3. 執行 node check_words.js，必須通過
4. 通過後才 commit，訊息格式：feat: 新增 N 個「主題」單字
description 是整份技能最重要的一行

工具不會每次都讀完你所有技能的內容——它先看 description，判斷這次的請求符不符合，符合才把整份讀進來。所以：

❌ description: 單字相關——太模糊，該觸發的時候不會觸發。
✅ description: 新增或修改 words.js 的單字時使用。包含格式規範、重複檢查與提交前的驗證流程。——寫清楚什麼時候該用，而不是「這是什麼」。

技能寫好卻從來不被觸發，九成是 description 的問題，不是內容的問題。

子代理：把雜活外包出去，順便保護你的上下文

另一個工具是子代理（subagent）：你派一個助手去辦一件事，它在自己獨立的上下文視窗裡把事情做完，然後只把結論回報給你。

為什麼這件事重要？回想 5.2：上下文是預算。假設你要它「檢查整個倉庫有沒有殘留的金鑰」——這件事得讀過幾十個檔案。如果在主對話裡做，那幾十個檔案的內容全部留在你的上下文裡，把你原本正在進行的工作擠出去。派子代理去做，回來的只有一句「檢查完畢，未發現金鑰，已檢查 37 個檔案」。

四種工具，怎麼選

到這裡你手上有四種「讓 AI 照你的方式做事」的辦法。它們不是替代關係，是不同的作用範圍：

工具什麼時候生效適合放什麼VocaBuddy 的例子
一次性提示只有這一句話臨時的、不會再做第二次的事「把這個函式改名」
專案指示檔（5.4）每次啟動都讀永遠適用的隊規縮排、commit 格式、不要自動推遠端
技能請求符合 description 時某一類任務的固定步驟新增單字的完整流程
子代理你派它出去時要讀很多、但只需要結論的雜活全倉庫金鑰檢查、code review

各家工具放這些檔案的位置不同，例如子代理：Claude Code 在 .claude/agents/、Codex 在 .codex/agents/、Gemini CLI 在 .gemini/agents/、Cursor 在 .cursor/agents/。技能的位置也各有各的（Codex 與 Antigravity 是 .agents/skills、Copilot 是 .github/skills）。不用背——Lab 13 第一步就教你怎麼問出來。

子代理不是免死金牌

子代理可以幫你先審一遍程式碼，但它不取代第一篇 1.7 的人審。理由很簡單：機器管「壞了沒」，人管「好不好」——這句話在第四篇 4.3 講 CI 時就出現過，這裡完全適用。一個由 AI 寫、AI 審、沒有人看過的 PR，掛的還是你的名字。

Lab 13：你的第一個技能

目標把「新增單字」的完整流程包成一個技能，並驗證它會在該觸發的時候觸發
時間約 45 分鐘
前置Lab 12 完成；倉庫裡有 words.js 與 check_words.js（第三篇 Sprint 4；沒做過的話，用你倉庫裡任一個重複性流程代替）

  1. 問出技能檔要放哪——順便練一個 AI-Native 的習慣

    各家工具的技能資料夾位置不同，而且會改。不要去背，也不要去猜，直接問你手上的工具：

    技能（skill）檔案在你這裡要放在哪個資料夾？請給我確切路徑，
並說明 SKILL.md 的 frontmatter 有哪些必填欄位。

    這是本篇想給你的一個習慣：會變的細節，問當下最新的來源，而不是憑記憶。（若它答得含糊，去看它官方文件的 Skills 頁——網址見附錄 B。）

  2. 先想清楚：你要包的是哪件事

    選題標準只有一條——你已經重複講過至少兩次的事。本 Lab 用「新增單字」示範，因為它步驟固定、有驗證、又接得上第三篇的 check_words.js。

    動手前先用一句話寫下：「當我想做 ＿＿＿＿ 的時候，我希望它自動照著 ＿＿＿＿ 做。」這句話等一下會變成 description。

  3. 建立技能，把 description 當成主角來寫

    在步驟 1 問到的位置建一個資料夾（例如 add-words），裡面放 SKILL.md：

    ---
name: add-words
description: 新增或修改 words.js 的單字時使用。包含格式規範、
  重複檢查，以及提交前必跑的 check_words.js 驗證流程。
---

# 新增單字流程

1. 先讀 words.js 確認現有格式：每筆是 {en, zh} 兩個欄位，不要自創欄位
2. 新單字加在陣列最後，不要重排既有順序（減少 PR 的無謂差異）
3. 執行 `node check_words.js`，必須看到「檢查通過」才算完成
4. 若報「重複單字」，把重複的那筆移除，重跑
5. 通過後才 commit，訊息格式：feat: 新增 N 個「主題」單字
6. 不要自動推遠端，push 由人執行

    注意第 6 條——它把 5.3 的紅線寫進了技能。紅線要寫在每一個它會讀到的地方，不要只寫一次。

  4. 驗證它真的會被觸發（本 Lab 的重點）

    寫好不等於會用。用一個不提示的請求來驗：

    • 清空目前工作階段（5.2）；
    • 用最自然的講法下指令，完全不要提到你的技能：「幫我加三個天氣主題的單字。」
    • 觀察它有沒有自動做到：讀格式 → 加在最後 → 跑 check_words.js → 用規定的 commit 訊息 → 沒有自作主張 push。

    全中，技能生效了。只做到一半——那是 description 不夠精準（見下方「卡住了？」①）。

  5. 再加一個負面測試

    換一個不相干的請求：「幫我把卡片的圓角改大一點。」它不應該去跑 check_words.js。技能該觸發時觸發、不該觸發時安靜，兩邊都對才算成功——這跟你在 Sprint 4 寫 check_words.js 時「故意加一個重複字看它擋不擋得住」是同一種驗證思維。

  6. 進版控、發 PR

    $ git switch -c feature/skill-add-words
$ git add .
$ git commit -m "feat: 新增 add-words 技能，統一新增單字流程"
$ git push -u origin feature/skill-add-words

    PR 描述用第一篇 1.7 的三段式，「怎麼驗證」直接寫你步驟 4、5 的兩個測試。技能跟指示檔一樣要進 Git——它是隊伍的共同資產，不是你的個人設定。

卡住了？

① 該觸發時沒觸發——先改 description，不要改內容。把「什麼時候該用」寫得更具體，並把使用者可能會用的說法寫進去（「單字」「words.js」「字表」）。
② 不該觸發時亂觸發——description 寫太廣了（例如只寫「單字相關」）。加上限定條件。
③ 它說找不到技能——資料夾位置錯了（回步驟 1 再問一次），或檔名不是 SKILL.md（大小寫要對），或沒有清空舊工作階段。
④ frontmatter 報錯——YAML 對縮排與冒號敏感（第四篇 4.3 寫 CI 時踩過同樣的坑）。確認 --- 上下各一行、冒號後有一個空格、多行描述的續行有縮排。

情境

它跑了十分鐘，最後說：「已完成修正，並已執行測試，全部通過。」你看了一眼，覺得合理，commit、push。兩天後隊友發現那個功能根本沒好——而且測試從頭到尾沒被跑起來過。

最重要的一句話

「它說測試通過」不等於「測試通過」。

模型是在生成一段合理的文字（第二篇 2.1），「測試全部通過」是一句非常合理的文字。要知道測試有沒有通過，只有一個辦法：你自己看到那個輸出。

看得越少，要驗得越重

驗證要花多少力氣，不是看任務難不難，是看你剛才盯了多少：

三個驗證動作，照順序做

順序動作在找什麼
1git diff 逐行讀它改了哪些你沒要它改的地方。這比「改對了沒」更常出問題
2自己跑一次真的能跑嗎？走一次完整的使用者流程，不是只看它有沒有噴錯
3自己跑測試，看到輸出node test_srs.js 印出「4 tests passed ✓」——你親眼看到那一行

第三篇你寫的 test_srs.js 與 check_words.js，在這一篇有了新意義：它們是你驗收 AI 產出的工具。測試寫得越好，你越敢放手——這不是巧合，是同一件事的兩面。

還記得 4.3 那句話嗎

「機器管『壞了沒』，人管『好不好』。」現在多了一層：當寫程式的也是機器，那道 CI 的綠勾就更重要了——它是唯一不會替自己說好話的環節。把 AI 產出接進 CI，比多讀十遍 diff 有效。

留痕：你的歷史就是你的證據

用 AI 開發不需要遮遮掩掩，但需要誠實而且留得住痕跡。三個習慣：

  • 照常走 GitHub Flow：issue → 分支 → PR → review → merge。AI 參與與否，流程一樣。歷史完整，別人才知道每個決定是什麼時候、為什麼發生的；
  • commit 訊息寫「做了什麼」，不寫「誰寫的」：這是第一篇 1.4 的規矩，沒有例外。若你的隊伍或主辦單位另有揭露規定，依規定辦理；
  • 你要能解釋每一行：這是第三篇篇首就立下的規矩——「AI 寫的每一行你都要能解釋」。在需要當場說明的場合（口試、Demo、評審提問），這條規矩就是你的保險。
一句話收尾

工具會換、模型會更新、指令會改名。但有一件事不會變：作品掛的是你的名字。它寫的、你送出去的，就是你的。

第二篇・AI 與 LLM／2.1

語言模型在做什麼

情境

你在手機上打「我今天要去」，鍵盤跳出三個候選：「上學」「補習」「睡覺」。鍵盤怎麼知道？它統計了大量文字，算出「我今天要去」後面最常接什麼。LLM 做的是同一件事——只是規模大了十億倍，大到產生了質變。

語言模型（Language Model）的定義只有一行：給定前文，輸出「下一個 token」的機率分布。用你熟的符號寫：

P(下一個 token | 前面所有 token)

注意它輸出的不是一個答案，而是一整張機率分布——詞彙表裡每個 token 各有一個機率，總和為 1。「生成一段文字」則是把這個一步驟重複執行：算分布 → 抽一個 token → 接到句尾 → 用新句子再算一次分布……直到抽中「停止」符號。這個一次生一格的方式稱為自迴歸（autoregressive）生成。

核心觀念

LLM 內部沒有資料庫、沒有搜尋、沒有「事實查核」模組——只有這張分布。它說「巴黎是法國首都」，是因為訓練資料讓這個接續的機率極高；它偶爾一本正經地瞎掰（稱為幻覺，hallucination），是因為對它來說「機率高的流暢句子」與「真話」本來就是兩回事。理解這一點，你就知道：AI 的輸出永遠要驗證——尤其是程式碼與事實。

那「大型」是大在哪？模型是一個有數十億到上兆個參數的神經網路，訓練就是在海量文字上不斷調整這些參數，讓它預測下一個 token 越準越好。神奇之處在於：當「預測下一個字」被逼到極致，模型必須學會文法、常識、推理、甚至寫程式——因為不懂這些，就預測不準。這是本章唯一需要你「先接受再體會」的事實，其餘全部可以推導。

第二篇・AI 與 LLM／2.2

Token 與 embedding：文字如何變成數字

情境

你問模型：「strawberry 裡有幾個 r？」它自信地答錯。一個會寫作業的 AI，居然數不對字母？因為它從頭到尾沒看過字母——它看到的是 token。

神經網路只吃數字，所以文字進模型前要先過兩道轉換：

  • Token 化（tokenization）：把文字切成小單位。不是按字母、也不完全按單字，而是按「常見程度」：常見單字整顆一枚 token，少見單字拆成幾個碎片。中文通常一到兩個字一枚。
  • Embedding（詞嵌入）：查表把每個 token 換成一個高維向量（幾千維的實數陣列）。這張表是訓練出來的，而且有個美妙性質：意義相近的 token，向量也相近。
給競程選手的翻譯

把 embedding 想成一本超大的字典：輸入一個 token，翻到那一頁，抄下上面那 n 個數字。這種「給定輸入直接查出預存的輸出、中間不做計算」的對應，叫查表（lookup table）。寫成映射：

embed:token↦ℝn讀作「吃進一個 token，吐出一個 n 維實數向量」——ℝ 是實數集合，ℝⁿ 就是 n 個實數排成一列

有了向量，「語意相似」就被實作成「兩向量的夾角小」，用餘弦相似度（cosine similarity）衡量：內積（dot product）除以兩向量模長（norm）的乘積：

cos⁡θ=a·b‖a‖‖b‖夾角小 → cos θ 接近 1 → 語意相近（除以模長乘積，是為了只比方向、不比長度）

檢索的世界從這裡展開：給一個查詢向量、在一堆向量中找最靠近的那個，叫最近鄰搜尋（nearest neighbor search, NNS）——可以看作你寫過一百次的最近點對問題（closest pair of points）的「線上版」：把「集合內找最近的一對」換成「找離查詢點最近的那一個」，同一套幾何距離的功夫。第三篇會先做檢索的雛形（用你的答題錯誤率當相關性分數）；把單字解釋轉成向量做真正的語意搜尋，則收錄在第四篇的畢業挑戰選項（見 4.5）。

現在你能解釋的怪事

數不對 strawberry 的 r——它看到的是 straw|berry 兩枚 token，不是 10 個字母；不擅長精確算術——「1234×5678」對它是幾枚 token 的接龍，不是位值運算；中英文計費不同——同樣意思的中文往往用掉更多 token。怪癖都不神祕，全是 token 的形狀。

第二篇・AI 與 LLM／2.3

Attention 直觀：模型怎麼「回頭看」

情境

翻譯這句：「I went to the bank.」——是銀行還是河岸？你會下意識地掃前後文找線索。模型也需要一個機制，讓每個字能「回頭看」其他字、決定該參考誰。這個機制叫 attention（注意力）。

2.2 說過每個 token 是一個向量。但「bank」如果永遠是同一個向量，就永遠分不出銀行與河岸。attention 的工作：讓每個 token 的向量吸收上下文。做法用一句話說完——

每個 token 對前文所有 token 打一個「相關性分數」，把分數化成權重（用 softmax——把一組分數壓成總和為 1 的機率分布的函數，2.4 會正式介紹），然後拿大家的向量做加權平均，得到自己的新向量。分數高的字，話語權就大。

給競程選手的翻譯

attention 一輪＝對每對 (i, j) 算相似度（向量內積）→ 對每個 i 做 softmax 得到權重列 → 加權平均。是的，樸素實作就是 O(n²)——這正是長文本又慢又貴的根本原因，也是為什麼 context window（下一節）是有限的。一個機制、一個複雜度，解釋了一堆產品限制。

這就是 softmax 加了溫度參數：z 除以 T 再取指數歸一化。T→0 時等價於 argmax；T→∞ 時趨近均勻分布——temperature 其實是在調分布的熵。另一顆常見旋鈕 top-p：把 token 按機率排序，只保留「累積機率 ≥ p」的前綴再取樣——尾巴上的 banana 們直接出局。全部都是你熟的機率操作，沒有新數學。

context window：模型的工作記憶

模型一次能「看見」的 token 總量有上限，稱為 context window（上下文窗口）——prompt、對話歷史、它自己的回答，全部算在裡面。超過了，最早的內容就等於不存在。

與錢包直接相關

API 按 token 計費：輸入（你塞進窗口的一切）＋輸出（它生成的一切）分開計價。prompt 越長、對話越久，越貴。養成習慣：只給模型「這次任務需要的」內容——省錢，而且窗口越乾淨、表現通常越好。

雲端 LLM：以 Claude API 為例

情境

VocaBuddy 有 500 個單字，你想每個都配一個例句。手寫？寫到畢業。在聊天視窗一個一個問 AI 再複製貼上？也要一整晚。你需要的是讓「程式」去問 AI——這就是 API 的用途。

API（Application Programming Interface，應用程式介面）是服務開給程式呼叫的窗口。雲端 LLM 的 API 本質上就是一個 HTTPS 請求：你的程式把訊息包成 JSON 送過去，伺服器上的模型算完，把回答包成 JSON 送回來。以 Claude API 為例，一次呼叫的三個要素：

  • API key（金鑰）：你的身分憑證，隨請求送出，用來認人與計費。它等於你的錢包，永遠不進 Git、不寫進程式碼——放在環境變數裡；
  • system prompt（系統提示）：這場對話的「人設與規則」，例如「你是高中英語老師，例句用 CEFR B1 難度」（CEFR＝歐洲語言共同參考架構 Common European Framework of Reference 的分級，B1 約高中程度）；
  • messages（訊息列）：對話內容本體，由 user（你）與 assistant（模型）的訊息交替組成。

用官方 Python SDK（software development kit，軟體開發套件），這整趟旅程是十行程式：

import anthropic

MODEL = "claude-sonnet-5-5"   # 模型名稱會更新，最新值見附錄 B

client = anthropic.Anthropic()          # 自動讀取環境變數 ANTHROPIC_API_KEY
msg = client.messages.create(
    model=MODEL,
    max_tokens=2000,                    # 這個額度也包含模型「想」的部分，見下方
    system="你是高中英語老師，例句使用 CEFR B1 難度。",
    messages=[{"role": "user",
               "content": "用單字 interval 造一個例句，附中文翻譯。"}],
)
print("".join(b.text for b in msg.content if b.type == "text"))
回應是一列「區塊」，不是一個字串

msg.content 不是字串，是一個區塊列表。新一代模型預設會「先想再答」，所以第一個區塊常常是 thinking（內容對你隱藏），文字答案在後面的 text 區塊裡。直接拿 content[0].text 會噴 AttributeError: 'ThinkingBlock' object has no attribute 'text'。正確作法是依 type 把所有 text 區塊挑出來接起來——上面最後那一行就是。
會不會出現 thinking 區塊取決於你的 prompt，同一支程式也不是每次都一樣（實測：自由文字的 prompt 三次都有，「只回 JSON」的 prompt 八次都沒有）。所以一律依 type 挑，不要賭 content[0]。

max_tokens 把「想」的 token 也算進去

模型思考用掉的 token 也算在 max_tokens 裡。像上面這種自由文字的請求，模型會先想一陣子，max_tokens=300 幾乎全被想掉，印出來是空白或半句話——而且不會報錯，這是最難查的那種 bug。判斷方法：看 msg.stop_reason，是 "max_tokens" 就代表額度不夠。自由文字給 2000；「只回 JSON」的請求 1024 夠用。想親眼觀察就把 msg.stop_reason 和 msg.usage.output_tokens 一起印出來。

金鑰三戒

一、不寫進程式碼，只放環境變數（ANTHROPIC_API_KEY）；二、不 commit 進 Git——進了歷史就等於公開，第一篇教過；三、真的洩漏了，立刻到主控台撤銷（revoke）那把 key 再發新的。申請方式與免費額度見附錄 B 時效資訊表。

別跟第五篇搞混了

這一節是你寫程式，程式去呼叫模型——模型是你程式裡的一個函式，產出是「一個會呼叫 AI 的功能」。
第五篇反過來：模型幫你寫程式——模型是你工作流裡的一個角色，產出是「一份被 AI 幫忙寫出來的程式碼」。
兩件事都要會，但方向相反，別混在一起想。

本地 LLM：以 Qwen 為例

情境

比賽當天，會場網路突然塞爆，雲端 API 逾時；或者你想處理的資料很私密，不想送出門；又或者你只是想在捷運上沒網路也能開發。解法：把模型裝進自己的電腦。開源模型＋一個叫 Ollama 的工具，一行指令就能跑。

有些模型公開釋出權重（訓練好的那幾百億個參數），任何人都能下載到自己的機器上執行，稱為開源（open-weight）模型——Qwen、Llama、Gemma 都是知名家族。本教材以 Qwen3.6-35B-A3B 為例，先解碼這串型號——它濃縮了兩個重要概念：

  • 35B：總參數量 350 億（B＝billion）；
  • A3B：每次推理只啟用（Active）30 億參數——因為它是 MoE 架構。

計算省了，記憶體怎麼辦？靠量化（quantization）：把每個參數從 16 bit 浮點數壓到 4 bit 左右的低精度表示，體積縮到約四分之一，能力只降一點點。35B 模型量化後大約 20 GB——高階筆電裝得下；記憶體較小的機器就換小一號的模型，原理完全相同（建議型號與硬體對照見附錄 B）。

Ollama：一行跑起來

Ollama 是本地模型的管理器：幫你下載、量化、載入模型，並在本機開一個與雲端同形的 API。安裝後：

$ ollama pull 模型名稱        # 下載模型（名稱見附錄 B），只需一次
$ ollama run 模型名稱         # 直接在終端機對話，Ctrl+D 離開
>>> 用 interval 造一個英文例句
>>> Trains depart at regular intervals of ten minutes. …

同時，Ollama 在 http://localhost:11434 開了 HTTP API（localhost＝「本機」的網路位址，只有你自己的電腦連得到；11434 是埠號 port——同一台電腦上區分不同服務的門牌號）——注意這件事的意義：對你的程式來說，本地模型跟雲端模型長得幾乎一樣，都是「送 JSON、收 JSON」。Lab 4 就利用這一點，寫一支可以自由切換兩者的程式。

核心觀念

雲端與本地不是信仰之爭，是工程取捨。而因為兩者介面同形，你的程式可以把「用哪個模型」變成一個參數——這個小小的設計決定（adapter 模式），會在斷網的比賽現場救你一命。

    import os, sys, json
import anthropic

MODEL = "claude-sonnet-5-5"   # 最新名稱見附錄 B
PROMPT = ("為英文單字「{word}」產生學習卡內容。只回傳 JSON，不要其他文字，不要 markdown 圍欄，"
          '格式：{{"word": "...", "sentence": "...", "zh": "...", "tip": "..."}}。'
          "sentence 用 CEFR B1 難度，且必須包含該單字。")
FALLBACK = {"sentence": "Practice makes perfect.",
            "zh": "熟能生巧。", "tip": "（預設內容：AI 暫時不可用）"}

def text_of(msg):                         # 依 type 只挑文字區塊，理由同 v1
    return "".join(b.text for b in msg.content if b.type == "text")

def ask(client, word):
    msg = client.messages.create(
        model=MODEL, max_tokens=1024,     # JSON 約 150～200 token，留餘裕給可能出現的 thinking
        system="你是高中英語老師。只輸出 JSON。",
        messages=[{"role": "user", "content": PROMPT.format(word=word)}],
    )
    return text_of(msg)

def generate(word):
    if not os.environ.get("ANTHROPIC_API_KEY"):
        print("沒有 API key，改用預設內容。", file=sys.stderr)
        return {"word": word, **FALLBACK}
    client = anthropic.Anthropic()        # 建在檢查之後，沒 key 時才接得到降階
    for attempt in range(2):              # 失敗最多重試一次
        try:
            data = json.loads(ask(client, word))
            if word.lower() in data["sentence"].lower():
                return data               # 驗證通過才放行
        except (json.JSONDecodeError, KeyError, TypeError, anthropic.APIError):
            pass
    return {"word": word, **FALLBACK}     # 降階：永遠有東西可給

if __name__ == "__main__":
    word = sys.argv[1] if len(sys.argv) > 1 else "interval"
    print(json.dumps(generate(word), ensure_ascii=False, indent=2))

本輪新知

① fetch 與 async/await：JavaScript 版的「發 HTTP 請求」。await fetch(url, {...}) 發出請求，await res.json() 解析回應——語意跟 Python 的 requests 一模一樣，只是多了 async 標記（因為瀏覽器不能停下來等）。

② Structured Output（結構化輸出）：要把 AI 輸出接進 UI，就要讓它回固定形狀的 JSON。兩件事做好就夠：system prompt 給出完整的 JSON 骨架範例（並明說「不要 markdown 圍欄」）、程式端 JSON.parse＋欄位驗證把關。

③ 金鑰安全，前端版——這是本輪最重要的觀念：

前端藏不住任何祕密

網頁的所有程式碼都會下載到訪客的瀏覽器，右鍵「檢視原始碼」一覽無遺——把你的 API key 寫進公開網頁，等於把錢包放在路邊。個人工具的正解是「使用者自帶金鑰」：key 由使用者輸入、只存在他自己的 localStorage、直接從他的瀏覽器呼叫 API。要做「內建 AI 的公開服務」則需要自己的後端代理——那是第四篇之後的進階路線。

④ 快取（cache）：同一個單字的例句不必生成兩次。生成過就存進 localStorage，下次直接用——省錢、變快、離線也能看。AI 應用的黃金習慣。

Sprint 3：SRS 排程——你的主場到了

情境

8 個單字每天全複習沒問題；學測 4500 字呢？每天全看一遍是自殺，隨機抽又會漏掉快忘的字。「在對的時間複習對的卡」是一個排程問題——也就是說，是一道演算法題。歡迎回到主場。

本輪新知

① 遺忘曲線（forgetting curve）：記憶保留率隨時間指數衰減（Ebbinghaus，1885）。但每次成功回想後，曲線會重置、而且衰減得更慢——所以最佳策略是：在快忘未忘之際複習，且間隔逐次拉長。這就是間隔重複系統（SRS）的全部理論基礎。

② Leitner 盒（萊特納盒，Leitner system）：SRS 最優雅的實作。5 個盒子，間隔 1／2／4／8／16 天：答對晉一級（間隔加倍），答錯打回盒 1。規則兩行，效果驚人。先玩再寫——

③ 純函式與單元測試：排程規則寫成一個純函式——不碰畫面、不自己看時鐘，輸入什麼就決定輸出什麼。純函式可以用單元測試釘死行為：測試先寫清楚「答對從盒 3 到盒 4、間隔 8 天」，程式改壞立刻被抓到。競賽裡你用測資驗演算法，工程裡一模一樣——只是測資自己寫。

④ 進階閱讀：SM-2：Anki 用的演算法。核心多一個「容易度係數 EF」：每張卡依你答題的順暢程度微調自己的間隔倍率（預設 2.5，答得吃力就降）。Leitner 是 SM-2 的階梯版；本輪實作 Leitner（規則簡單、好測試），把 SM-2 留給畢業挑戰。

部署：GitHub Pages

情境

你想讓同學試用 VocaBuddy，於是把整包檔案傳進群組，然後開始遠端教學：「先解壓縮，對，然後點 index.html……」三個人裡兩個卡住。正確的做法是給一個網址——點開就能用。把檔案放上一台永遠開機的伺服器，就叫部署（deploy）。

好消息：VocaBuddy 是靜態網站——只有 HTML／CSS／JS 檔案，不需要在伺服器上跑程式（所有邏輯都在使用者的瀏覽器裡執行）。靜態網站的部署極其簡單，而你的程式碼已經住在 GitHub 上了——GitHub Pages 就是 GitHub 內建的免費靜態網站主機：指定一個分支，它就把裡面的檔案發布成網站。

上線前的一道安檢

免費方案的 Pages 需要 repo 轉為 public（公開）——公開的是整個倉庫，包含全部歷史。轉公開前必做：git grep sk-ant-api（真金鑰長成 sk-ant-api03- 開頭的長字串；只搜 sk- 會把說明文字和示範用的假 key 一起撈出來，嚇自己一跳）、再用 git log -p -S'sk-ant-api' --all 掃過整個歷史，確認任何 commit 都沒帶過金鑰或個資。萬一真有：撤銷那把 key（historical 的內容洗不乾淨，換鑰匙最快），再公開。

核心觀念

注意這條流水線的形狀：main 分支＝正式版。第一篇立的規矩（main 永遠可用、改動走 PR）到這裡兌現出真正的意義——因為現在 main 上的每個 commit，都會在一分鐘後出現在全世界面前。流程不是儀式，是上線紀律。

設定只要三個點擊，完整步驟在 Lab 9。網址格式是 你的帳號.github.io/倉庫名——這也是為什麼教材從 Sprint 2 起所有路徑都用相對路徑（sw.js 而非 /sw.js）：部署在子路徑下才不會斷連結。

PWA：讓網頁像一個 App

情境

同學試用後說：「不錯欸，可是每次都要開瀏覽器打網址，還是 App 方便。」你沒有時間學兩套原生開發（iOS＋Android），也沒有上架費。好消息：加兩個小檔案，你的網頁就能「安裝」到手機主畫面、全螢幕開啟、離線使用——這就是漸進式網頁應用（Progressive Web App, PWA）。

兩個檔案各司其職：

① manifest.json——App 的身分證。告訴瀏覽器這個網站叫什麼、用什麼圖示、要不要獨立視窗：

{
  "name": "YTP VocaBuddy 背單字夥伴",
  "short_name": "VocaBuddy",
  "start_url": ".",
  "display": "standalone",
  "background_color": "#f4f6f5",
  "theme_color": "#0f766e",
  "icons": [{ "src": "icon.png", "sizes": "512x512", "type": "image/png" }]
}

② sw.js——離線的小管家。service worker 是一支常駐在瀏覽器背景的腳本，能攔截這個網站的所有網路請求。最簡策略「快取優先」十行寫完：

const CACHE = "ytp-vocabuddy-v1";     // 改版時把 v1 改成 v2，舊快取才會換新
const SHELL = ["./", "index.html", "words.js", "srs.js", "manifest.json", "icon.png"];

self.addEventListener("install", e => {
  e.waitUntil(caches.open(CACHE).then(c => c.addAll(SHELL)));   // 安裝時先存一份
});

self.addEventListener("fetch", e => {
  e.respondWith(
    caches.match(e.request).then(hit => hit || fetch(e.request)) // 先問快取，沒有才上網
  );
});

回想 Sprint 2 的設計紅利：AI 例句本來就有 localStorage 快取、學習紀錄本來就在本機——所以離線時複習、統計、看過的例句全部照常，只有「生成新例句」需要網路。當初的架構決定，現在自動變成離線體驗。

service worker 的黏性

快取很「黏」：改了程式碼卻看到舊版，是 PWA 開發第一名的困惑。兩個習慣：每次改版把 CACHE 名稱 v1 → v2（舊快取即作廢）；開發時打開 DevTools → Application → Service Workers 勾「Update on reload」。

GitHub Actions：品質檢查自動發生

情境

Sprint 4 之後，你們的紀律是「merge 前要跑 node test_srs.js 和 node check_words.js」。第一週大家都記得；第三週某個深夜，一個沒跑測試的 PR 合進了 main——而 main 現在直通正式網站。靠「記得」的紀律終究會失守。解法：讓 GitHub 替你記得——每次 push 自動跑，這就是持續整合（CI）。

GitHub Actions 是 GitHub 內建的自動化服務：你在 repo 裡放一個「劇本」（workflow），指定什麼事件發生時、在什麼機器上、跑哪些指令。劇本用 YAML 格式寫在 .github/workflows/ 資料夾：

# .github/workflows/ci.yml
name: CI
on:                             # 什麼時候跑
  push:
    branches: [main]            # 只在 main 有新 commit 時跑一次
  pull_request:                 # 以及每個 PR 跑一次

jobs:
  test:
    runs-on: ubuntu-latest      # 在哪跑：GitHub 提供的乾淨 Linux 機器
    steps:
      - uses: actions/checkout@v4      # 現成積木：抓下你的程式碼（版本見附錄 B）
      - uses: actions/setup-node@v4    # 現成積木：裝好 Node
      - run: node test_srs.js          # 跑你的單元測試
      - run: node check_words.js       # 跑你的資料檢查
核心觀念

CI 的價值不是「多跑幾次測試」，是把品質從個人自律變成系統保證。第三篇你寫的 test_srs.js 與 check_words.js 本來就是為這一刻準備的——測試寫得好，自動化只是把它接上電。順帶一提：4.1 的 Pages 部署，底層跑的正是 Actions——你早就在用它了。

加碼一行：在 README 放上狀態徽章（badge），別人一眼看到你的 repo 是綠的——Actions 分頁 → 選 workflow → ⋯ → Create status badge，把產生的 Markdown 貼進 README 即可。

線上課的助教在做什麼——以及為什麼自學者不需要他們

這份教材的每一個 Lab 都寫到「沒有人在旁邊也走得完」：安裝寫成三個共通步驟＋自助排錯，每個 Lab 附「卡住了？」六條症狀對照。導讀也對學生明說了這件事。

那線上課還要助教做什麼？壓縮時間，以及處理個案。一場 3–4 小時的線上課有硬性的時間邊界，不能讓一位學生的環境問題卡住全班。助教的三項工作：

  • 課前 30 分鐘技術支援時段——這是投報率最高的一項。把安裝問題擋在正課之前，正課才跑得完；
  • 課中巡場——實作時間逐一確認每位學生的畫面到位；卡超過 5 分鐘就介入；
  • 課後彙整——把當天真實發生的卡關收成清單，回饋給教材維護者補進「卡住了？」。
一條界線

助教不要替學生打指令。替他打完，他當天過關、比賽當天照樣卡住。正確作法是指到教材的哪一段，讓他自己做完——因為競賽現場沒有助教。
